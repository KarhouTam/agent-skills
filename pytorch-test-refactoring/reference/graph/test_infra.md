# Graph-mode test infrastructure

Field knowledge for the `graph` refactoring field. It describes how the tests in the field are
built, which mechanisms create their test methods and classes, where they couple to a device or to
a compile backend, and what breaks silently when they are reorganized.

This is **advisory reference material, not an enforced ruleset**. The graph field has no
field-specific refactoring profile yet, so `utils.compute_applicable_rules()` still returns
`["cleanup"]` for it and the baseline prompts still forbid device-decoupling edits. Read this
document to make those edits *correct* when the profile lands, not as a licence to change test
semantics.

All counts were generated by `scripts/graph_test_infra_census.py` at commit `79f8150273e` and are
counted over the field list's own files, not over whole directories. Regenerate with:

```bash
python3 scripts/graph_test_infra_census.py --repo /path/to/pytorch --write
```

Full output: `reference/graph/test_infra_census.md` (readable) and
`reference/graph/test_infra_census.json` (machine-readable).

The two dynamo/inductor classes are both *named* `TestCase`; only the import site says which one a
file gets. `from torch._dynamo.test_case import TestCase` and `from torch._inductor.test_case import
TestCase` are the two spellings, and `from torch._inductor.test_case import TestCase as
InductorTestCase` is common in inductor files. Base count per family (AST, harness bases only):
inductor `TestCase` 356 / `InductorTestCase` 75, dynamo `torch._dynamo.test_case.TestCase` 222 /
`TestCase` 74, export `TestCase` 45, fx `TestCase` 45 / `JitTestCase` 13, aoti `TestCase` 19, onnx
`common_utils.TestCase` 31 / `pytorch_test_common.ExportTestCase` 9.

Three consequences that matter during refactoring:

* **`DynamoTestCase` does not reset Dynamo.** The reset lives in `common_utils.TestCase._run_custom`
  via `_reset_dynamo_if_imported()`:3903-3909, entered at :4075-4083 and :4169-4174. A subclass that
  overrides `run()`/`_run_custom()` without chaining loses cross-test isolation. Note
  `torch/_dynamo/CLAUDE.md` still claims the base class resets in setUp/tearDown -- that is stale.
* **Assertions can become no-ops.** Under `config.debug_disable_compile_counter`, the dynamo
  `assertEqual` returns early for `CompileCounterInt` operands and for any assert whose caller line
  contains the word `counters` (`torch/_dynamo/test_case.py:200-214`), and `assertExpectedInline`
  returns early too (:216-220). A refactor that swaps a base class changes what is actually
  asserted.
* **`lint_test_case_extension` is a hard gate.** `run_tests` calls it before running
  (`common_utils.py:1518-1521`, definition :1367) and `sys.exit(1)`s if any discovered class does
  not derive from `common_utils.TestCase`. All in-scope harness bases do; a new base class built
  directly on `unittest.TestCase` will hard-fail the whole file.

## 2. Generation mechanisms

Five mechanisms create test methods or classes at collection time. Two of them generate *device*
matrices, three generate *mode/backend* matrices.

### 2.1 Parameterization

`parametrize`:810 attaches a `parametrize_fn` to the function through `_TestParametrizer`:621;
`instantiate_parametrized_tests`:732 replaces each decorated method with one method per argument
tuple, `delattr`-ing the template (:756) and naming each `f"{test.__name__}_{suffix}"`:770.

Constraints that fail silently:

* Parameter name order **is** decoration order (`compose_parametrize_fns`:673, naming at :702-704).
  Inserting a new `@parametrize` above an existing one renames every generated test, which
  invalidates CI selectors and `DecorateInfo.test_name` filters.
* Two stacked parametrizers owning the same parameter is a `RuntimeError` (:696-700) -- this one
  fails loudly.
* Generated names may not contain `.` (`validate_test_name`:714, called at :771), because
  `unittest.TestLoader.loadTestsFromName` splits on dots.
* `TestCase.__init_subclass__`:3798 calls `_omit_skipped_tests`:782-787 before class decorators run,
  so under `PYTORCH_TEST_OMIT_SKIPPED` a statically skipped template is dropped *before*
  instantiation -- the collected node-id set changes.

Scale in scope: `@parametrize` 355 uses in dynamo, 1341 in inductor, 43 in export; also
`instantiate_parametrized_tests` 194 in inductor and 95 in dynamo.

### 2.2 Device-type instantiation

`instantiate_device_type_tests(generic_test_class, scope, except_for=None, only_for=None,
include_lazy=False, allow_mps=False, allow_xpu=False)`:1261 synthesizes one class per desired device
type. Exact behaviour:

* It **deletes** the generic class from the caller's globals (`del scope[name]`:1272), names each
  generated class `generic.__name__ + base.device_type.upper()` (:1285), builds
  `type(class_name, (base, generic_test_class), {})` (:1289) so the device base wins on MRO,
  synthesizes `setUpClass`/`tearDownClass`:1295-1312, copies non-test members only when the device
  class lacks them (:1330-1334), re-injects into the caller's globals and copies `__module__`
  (:1340-1341), then `delattr`s every template test method (:1343-1348).
* It rewrites the `device` argument to `cls._init_and_get_primary_device()` (:646-657), and
  `deviceCountAtLeast` tests get the whole list as `devices` via param-kwarg rewriting (:303-319).
* It composes the dtype parametrization *inside* itself (:707-737) and assembles the final name as
  `f"{name}{test_suffix}{device_suffix}{dtype_suffix}"` (:739-774). That device-then-dtype order is
  exactly what `remove_device_and_dtype_suffixes` (`common_utils.py:3454-3465`) unwinds to map a
  generated name back to a CI-disabled-test entry.

Failure modes to design around:

* **A second call on the same class silently generates nothing** -- the template is already gone
  (:1272 destroys it). Someone adding a new accelerator subset by calling it twice gets zero tests.
* **It is not stackable with `instantiate_parametrized_tests`** on the same class. Device
  instantiation already consumes `parametrize_fn`; pre-instantiating deletes the template method
  (:756) and the device pass then finds nothing. The correct pattern applies them to different
  classes (see `test/test_fx_experimental.py:2469-2470`).
* **`@ops` requires a device context** and raises `RuntimeError` outside one
  (`common_device_type.py:1527-1532`).
* **`setUpClass` runs at import time** for CUDA/MPS/XPU/PrivateUse1 bases through
  `_init_and_get_primary_device`:574-582 -> :654, i.e. device initialization and MAGMA/cuDNN probing
  happen during collection, then again at run time.

### 2.3 Class cloning with patches (the mode/backend matrix)

Three generators clone a template class under a config patch and a name suffix:

| mechanism | defined at | generates | name rule |
|---|---|---|---|
| `make_test_cls_with_patches` | `torch/_dynamo/testing.py:493` | subclass with per-test `mock.patch.object` wrappers | class `f"{prefix}{cls.__name__}"`:501, methods `f"{name}{fn_suffix}"`:510 |
| `copy_tests` (+ `TestFailure`, `add_test_failures`) | `test/inductor/test_torchinductor.py:20650`, :20644, :20685 | copies `my_cls.__dict__` test methods onto an **existing** class | method `f"{name}_{suffix}"`:20680 |
| `make_test_cls_with_mocked_export` | `test/export/testing.py:157` | clones an export test class with `torch.export.export` monkeypatched | class `f"{cls_prefix}{cls.__name__}"`:165, methods `f"{name}{fn_suffix}"`:174 |

Consumers in scope: `make_test_cls_with_patches` in `test/dynamo/test_dynamic_shapes.py:40`
(6 config patches, `assume_static_by_default=False` among them), `test/inductor/test_halide.py`,
`test/inductor/test_pallas.py`, `test/dynamo/test_inline_and_install.py`,
`test/dynamo/test_nested_graph_breaks_wrapped.py`, `test/fx/test_graph_pickler.py`, and the
`_expected_failure_*` markers at `torch/_dynamo/testing.py:557/563/569`. `copy_tests` drives the
inductor device matrix (`test/inductor/test_torchinductor.py:20745` for CPU, :21054 for
`GPU_TYPE`), the dynamic-shape matrices (`test/inductor/test_torchinductor_dynamic_shapes.py:107`,
`test/inductor/test_torchinductor_codegen_dynamic_shapes.py:531`) and freezing
(`test/inductor/test_inductor_freezing.py:1071`, :1079). `make_test_cls_with_mocked_export` has
eight consumers (`test_export_strict.py:25`, `test_serdes.py:42`, `test_nativert.py:200`, ...), each
of which must re-inject the class into module globals -- the code says so itself:
`test/export/test_export_strict.py:33-36`, with the comment `# REMOVING THIS LINE WILL STOP TESTS
FROM RUNNING`.

Hazards:

* `make_test_cls_with_patches` iterates `dir(cls)` (:504), so inherited tests are re-emitted: editing
  a base-class test fans out into every generated matrix. Non-callable `test_*` attributes are
  copied **without** the suffix (:507-509), and the new class reuses `cls.__bases__` (:501), so MRO
  is shared with the original.
* `copy_tests` mutates a class that must already exist and keys `test_failures` dicts by *suffixed*
  string names with no validation against the template. Renaming a `CommonTemplate` test silently
  invalidates every entry.
* **The two mechanisms now coexist and do not compose.**
  `test/inductor/test_torchinductor_codegen_dynamic_shapes.py:711-716` migrated its GPU variant to
  `instantiate_device_type_tests(..., allow_xpu=True, except_for="cpu")`, and because device
  instantiation has no per-suffix failure hook, the file re-applies `test_failures` onto the
  generated `<Cls><SUFFIX>` classes by hand (:718-745). The comment there documents the gap and warns
  that on Python >= 3.12 `unittest.expectedFailure` mutates the shared template method in place.
  Unifying the mechanisms without porting that data loses skips silently.
* Export's suffix constants are a naming contract: `test/export/test_export.py:222-235`
  (`_nonstrict`, `_strict`, `serdes`, `_pre_dispatch`, ...), with the xfail marker decorators at
  `test/export/testing.py:208-288`.

### 2.4 OpInfo-driven generation

`@ops`:1509 in `torch/testing/_internal/common_device_type.py` generates one variant per
(OpInfo x dtype) from `op_db` (`torch/testing/_internal/common_methods_invocations.py:12066`), with
`skipOps`:1424 building per-op overrides from `DecorateInfo` (`torch/testing/_internal/opinfo/core.py:74`,
`is_active`:116). Two couplings matter:

* `OpInfo.get_decorators` is called with the **template** class name and the **undecorated** test
  name (`common_device_type.py:1643-1649`). Renaming a test method, or moving it to a differently
  named class, silently deactivates every `DecorateInfo` that selected it -- the skip simply stops
  applying, with no error.
* Op keys are `OpInfo.full_name` (`linalg.norm`), while generated test suffixes use
  `formatted_name` (`linalg_norm`). Mixing them yields a skip that never matches.

Scale in scope: `DecorateInfo` is used in export (`skipOps` 8, `@ops` 7) and inductor
(`@ops` 8, `skipOps` 4), and `op_db` is consumed by `test/inductor/test_torchinductor_opinfo.py`
and `test/export/test_export_opinfo.py`. This is the least-used mechanism of the five inside the
graph field, but it is the one the core field already has machinery for.

### 2.5 Programmatic generation

`test/test_fx.py:6152 generate_tests` -> `:6160 TestVisionTracing.generate_tests()` builds methods
with `setattr` (:6081), gated on `HAS_TORCHVISION`. `test/test_fx.py` is also the FX aggregator:
:51-68 imports every `test/fx/**` class into its own globals, which is the only way those tests are
discovered (section 4).

## 3. Sentinel ledgers

Five directories of empty files mark tests as skipped or expected-to-fail when the suite runs under
a compiler. A file's *name* is the key; its content is irrelevant.

| ledger | entries | device-suffixed keys |
|---|---:|---:|
| `test/dynamo_skips` | 3997 | 3515 |
| `test/dynamo_expected_failures` | 3791 | 139 |
| `test/inductor_skips` | 6 | 5 |
| `test/inductor_expected_failures` | 363 | 357 |
| `test/compiled_autograd_skips` | 1205 | 867 |

* **Key format** is `f"{self.__class__.__name__}.{self._testMethodName}"`
  (`common_utils.py:4014-4015`). Not `file::class::method`. `CPythonTestCase` overrides it to embed
  the file stem and Python version (`torch/_dynamo/test_case.py:289-298`), which is why 2770 of the
  dynamo expected-failure entries are `CPython*`.
* **The only enforcement point** is `common_utils.TestCase._run_custom`, gated on
  `TEST_WITH_TORCHDYNAMO or TEST_WITH_AOT_EAGER or TEST_WITH_TORCHINDUCTOR` (:4028): key lookup
  :4112, expected-failure wrap :4124-4134 (an unexpected pass raises `RuntimeError("Unexpected
  success, please remove ...")`), skip wrap :4136-4160, compiled-autograd wrap :4162-4165.
  `test/run_test.py` never references these directories.
* **Loading** is `find_test_dir()` (`torch/testing/_internal/dynamo_test_failures.py:29-56`), which
  probes `dirname(__file__)/../../../test` and then walks up from `__main__.__file__`. If it fails it
  logs a warning (:60-64) and **all five sets become empty** (:80-87) -- the whole xfail/skip surface
  disappears without an error. Import-time invariants: every name must split on `.` into exactly two
  parts (:123-130) and the skip/expected-failure sets must be disjoint (:132-144).
* **Regeneration** is `scripts/compile_tests/update_failures.py`, which rewrites entries from JUnit
  XML and `git rm`s files whose tests unexpectedly passed.

What breaks on a rename, in order of likelihood during a refactor:

1. Renaming a test method or class changes the key, so the ledger entry becomes an orphan: the test
   is no longer xfailed/skipped and fails for real under `PYTORCH_TEST_WITH_DYNAMO=1`. Nothing
   detects the orphan -- membership is the only check.
2. Because the ledger is 70-98% device-suffixed (table above), renaming or re-parametrizing a
   device-generated class can require migrating thousands of files. Making a *template* class
   device-generic does **not** make generated ids device-generic.
3. `CPythonTestCase` keys embed the file stem and version directory, so moving a `cpython/v3_13/*`
   file orphans its entries en masse.
4. Moving `test/` or renaming any of the five directories makes `find_test_dir()` return `None` and
   disables the entire surface.
5. Two same-named classes in different files collide, because the key has no module component.

## 4. Runner integration

* `TESTS` comes from `tools/testing/discover_tests.py:72`, built by globbing `test/**/test_*.py`
  (:41-43) minus prefix/exact blocklists. `test/fx` and `test/jit` are blocklisted as *patterns*
  (:77-78, "executed by test_fx.py" / "executed by test_jit.py"), which is why 23 of the 28 listed FX
  paths have no runner entry: they are only reachable through `test/test_fx.py:51-68`, and they end
  with `raise_on_run_directly("test/test_fx.py")` (`common_utils.py:1125`, e.g.
  `test/fx/test_common_passes.py:139`), which makes direct invocation an error.
* Family selectors are prefix filters over `TESTS`: `INDUCTOR_TESTS`:438, `DISTRIBUTED_TESTS`:439,
  `TORCH_EXPORT_TESTS`:440, `DYNAMO_CORE_TESTS`:445, `CPYTHON_TESTS`:446, `ONNX_TESTS`:447.
  `--dynamo`/`--inductor` set `PYTORCH_TEST_WITH_DYNAMO`/`PYTORCH_TEST_WITH_INDUCTOR` in the child
  environment (`test/run_test.py:2488`, :2491), which `common_utils.py:2053-2069` turns into
  `TEST_WITH_TORCHINDUCTOR`/`TEST_WITH_TORCHDYNAMO` **at import time**.
* ONNX is excluded by default and runs only with `--onnx` (`test/run_test.py:1633-1641`,
  :1945-1951); there is no `--export` selector, only `--exclude-torch-export-tests`.
* In-scope paths the runner does not execute: all 23 `test/fx/**` files, `test/onnx/test_models.py`,
  `test/onnx/test_onnxscript_no_runtime.py`, `test/onnx/test_pytorch_onnx_onnxruntime_cuda.py`,
  `test/onnx/model_defs/op_test.py`, and `test/inductor/test_aoti_cross_compile_windows.py`.
* `run_tests` for dynamo/inductor silently returns instead of running when
  `TEST_WITH_TORCHDYNAMO`/`TEST_WITH_CROSSREF` is set, on Windows without XPU, or when a `needs`
  dependency is missing (`torch/_dynamo/test_case.py:101-126`). The common_utils `run_tests`
  (`common_utils.py:1490`) does none of that, and files differ in which one they import, so swapping
  a base class without swapping `run_tests` changes behaviour under the `dynamo` CI config.

## 5. The two coupling axes

Graph-mode tests are coupled along two independent axes, and a refactor must decide which one it is
touching. The core field's vocabulary only covers the first.

**Device axis** -- which hardware a test runs on. Vocabulary in scope:

| mechanism | semantics |
|---|---|
| `instantiate_device_type_tests(only_for=/except_for=/allow_xpu=/allow_mps=)` | creates the per-device classes; `only_for`/`except_for` are the whitelist/blacklist at class level |
| `@onlyOn(dev)` and friends (`common_device_type.py:2008`, wrappers :2236-2262) | skip unless `dev in self.device_type` -- a **substring** test; on Sandcastle/fbcode it passes vacuously (:2019-2024) |
| `@onlyAccelerator`:2265 / `@onlyNativeDeviceTypes`:2063 | "any non-CPU/Meta device" / a fixed native-device tuple (`common_utils.py:491`) |
| `@skipCUDAIf` :1712, `@skipXPUIf` :1718, `@skipIfRocm` (`common_utils.py:2483`), `@skipMPS` | negative, per-device skips |
| `deviceCountAtLeast`:2036, `@dtypes`/`@dtypesIf*`:2175-2231, `largeTensorTest`:1909, `@expectedFailure(device_type)`:1972 | multi-device, per-device dtype and tolerance, memory-gated, device-specific xfail |
| `HAS_GPU`/`GPU_TYPE`/`HAS_CUDA_AND_TRITON` (`torch/testing/_internal/inductor_utils.py:74-85`), `@requires_gpu`/:199, `TEST_CUDA`, `torch.cuda.is_available()`, `torch.cuda.*`, `.cuda()`, `device="cuda"` | ad-hoc gating and hardcoded devices |
| env vars `PYTORCH_TESTING_DEVICE_ONLY_FOR` / `_EXCEPT_FOR` / `_FOR_CUSTOM` (`common_device_type.py:1136-1138`) | run-time device filtering without editing tests |

**Backend/mode axis** -- which compile backend and mode is under test. Vocabulary in scope:

| mechanism | semantics |
|---|---|
| `torch._dynamo.config.patch` / `torch._inductor.config.patch` / `torch._functorch.config.patch` | `ConfigModule.patch` (`torch/utils/_config_module.py:1179`); as a class decorator it returns a *subclass* whose `setUpClass` enters the patch (:1474-1505), so `type(obj) is Original` fails and collection-time reads are unpatched. 2419 decorator uses across the dynamo and inductor files of this field |
| `make_test_cls_with_patches` | one cloned class per mode (dynamic shapes, wrapped graph breaks, ...) |
| `copy_tests` + `TestFailure` | one suffixed test per (template x device) pair, with per-suffix skip/xfail data |
| `make_test_cls_with_mocked_export` + suffix constants | one cloned class per export flavor (strict, non-strict, serde, pre-dispatch, nativert, ...) |
| backend objects | `CompileCounter`, `CompileCounterWithBackend`, `EagerAndRecordGraphs`, `AotEagerAndRecordGraphs`, `InductorAndRecordGraphs` (`torch/_dynamo/testing.py:235-346`); `GPU_TYPE`/`GPU_TYPES` selection (`torch/_inductor/utils.py:147`, :252) |
| cudagraph modes, freezing, max-autotune, triton-vs-cpp | module/class-level config patches plus per-backend skips |

## 6. Refactoring implications

### 6.1 Target vocabulary

`HardwareClassification` (`common_utils.py:128-171`) is the in-tree declaration meant to replace
per-test device decorators, with `GENERIC` explicitly covering "shared, device-agnostic logic (e.g.
Dynamo dispatcher, FX passes, ...) that does not depend on a particular accelerator" and
`ACCELERATOR` covering tests that must hold on every accelerator and *are* device-instantiated.
That maps onto the two axes: `GENERIC` is the backend-axis value, `ACCELERATOR` and
`CPU`/`CUDA`/`MPS`/`XPU` are the device-axis values.

Suggested classification per family, and how much is already declared:

| family | suggested classification | already declares `hw_classification` |
|---|---|---|
| fx | `GENERIC` (FX passes and graph rewrites are device-free) | 21 files |
| dynamo | `GENERIC`, except cudagraph/stream/device-guard tests (`ACCELERATOR` or `CUDA`) | 50 files |
| inductor | `ACCELERATOR` for the device-parametrized core; `CUDA`/`XPU`/`MPS` for backend-specific files | 20 files |
| aoti | `ACCELERATOR` where device-parametrized; `CUDA` for the CUDA-only runtime/serialization tests | 4 files |
| export | `GENERIC` for graph-level tests; `ACCELERATOR` for the device-instantiated ones | 20 files |
| onnx | `GENERIC` (ONNX tests are device-free by design) | 27 files |

Declaration is enforced as a *type* check, not a presence check: `get_hw_classification`
(`common_utils.py:193-207`) raises `TypeError` if the attribute is not a `HardwareClassification`
member. Filtering happens in `HardwareClassificationTestLoader`:1439 via
`filter_by_hw_classification`:209, driven by `--hw-classification` (`test/run_test.py:1666`), and is
a no-op when the flag is absent.

### 6.2 Per-family hazards

* **fx** -- the 23 `test/fx/**` files are not runner-visible and not directly runnable
  (`raise_on_run_directly`). Any move or split must keep `test/test_fx.py:51-68` importing the class
  into its globals. Three files sit on `JitTestCase` rather than `TestCase`.
* **dynamo** -- `_dynamo_test_key` is `Class.method`, so the 3997-entry `dynamo_skips` ledger (88%
  device-suffixed) follows any rename. `test_ctx_manager.py` and `test_streams.py` are the device
  hot spots. `torch/_dynamo/CLAUDE.md`'s reset claim is stale.
* **inductor** -- the largest and most coupled family: the `copy_tests` matrix
  (`CommonTemplate` x {`cpu`, `GPU_TYPE`, `_dynamic_shapes`, `_codegen_dynamic_shapes`}) makes
  generated ids and ledger keys device-bearing, and `test/inductor_expected_failures` is 357/363
  device-suffixed. `test_torchinductor.py:387`'s local `TestCase` is imported by
  `test_xpu_basic.py`, and `GPU_TYPE` is part of every generated test id, so template-level
  genericity does not survive into the ids.
* **aoti** -- `copy_tests` is used here too (16 uses, 3 files), and the family shares inductor's
  bases; treat its matrix data like inductor's.
* **export** -- the suffix constants and the eight `make_test_cls_with_mocked_export` consumers form
  a naming contract; each cloned class must keep its `globals()[...]` re-injection.
* **onnx** -- self-contained bases; the CUDA runtime file is not runner-visible; dependency gating
  is handled by the runner, not in-file, so a missing `onnx`/`onnxruntime` must not be "fixed" by
  adding import guards in the test.

### 6.3 Do not

* Do not rename a test method or class without migrating the sentinel ledgers; orphans fail silently
  and are invisible to static checks.
* Do not stack `instantiate_parametrized_tests` on a class that is also passed to
  `instantiate_device_type_tests`, and do not call device instantiation twice on one class.
* Do not "convert" a device-suffixed generated id into a device-generic one by editing the template;
  the ids are produced by the generator and are keyed into the ledgers and CI selectors.
* Do not move `test/dynamo_skips`, `test/dynamo_expected_failures`, `test/inductor_skips`,
  `test/inductor_expected_failures` or `test/compiled_autograd_skips`, or relocate `test/` itself.
* Do not add import guards for `onnx`/`onnxruntime` inside ONNX tests; the runner already excludes
  them when the dependency is missing (`test/run_test.py:1282-1291`).
* Do not classify a graph test as device-agnostic because it creates tensors. The device axis in this
  field is carried by `GPU_TYPE`/`device="cuda"`/`only_for=`/`@requires_gpu`, not by tensor creation.
